## Part 1: the pilot, `GFXE.TRectangle` and `TRectangleList`

`TRectangle` (`src/Units/GFXE.cs`) has two split initializers, `Create__init_TRectangle` and
`CreateRect__init_TRectangle`, each behind a static factory with the guarded allocation.
`TRectangleList` only has a static `Create` over the raw allocation. Neither has a `Meta`
registration or a raw consumer. The callers are in `GFXE.cs` and `ImageLib.cs`.

1. `TRectangle` gets two real constructors, `TRectangle(int ALeft, int ATop, int ARight, int
   ABottom)` and `TRectangle(in TRect R)`, with the bodies of the two initializers and their
   `// GFXE.pas:line` comments. The initializers and the static factories go. No parameterless
   constructor remains.
2. `TRectangleList.Create()` goes and its callers use `new TRectangleList()`.
3. The callers use `new`. Nothing else in the classes changes.

A failure in these bodies is impossible (field assignments only), so the guarded factory has
nothing to clean up. Say so in the report with the reason. The frames and the full check are the
proof that values and order did not change.

## Part 2: the construction-failure contract

The game's guarded factories reproduce Delphi's rule: when a constructor called through a class
raises, the object's virtual destructor runs once, its inherited chain runs, and the exception
continues. Before any family that depends on it is converted, the rule gets a recorded oracle and
a proven C# shape.

1. **Delphi probe.** Extend `tests/probes/classes.pas`, or add a new probe program next to it,
   so the Delphi 3 recording covers:
   - failure in the base constructor body, in a middle class and in the most derived class of a
     three-level chain, each with the destructor chain it causes
   - a failing constructor that has already inserted the object into an owner's list, and the
     owner's list afterwards
   - a constructor that creates a child object whose own constructor fails, and what each of
     the two objects sees
   - a destructor that raises while cleaning up after a failed constructor, and which exception
     reaches the caller
   - a virtual method called from a base constructor that reads a field of the derived class
   - an inherited constructor called as a plain method (`inherited Create` on an existing
     object), which in Delphi does not allocate and does not clean up on failure

   Record it with `python tests/probes/run.py <name> --force`. The recording is the oracle for
   the rest of this part.
2. **The current split shape.** The probe's generated C# (the transpiler's output) passes
   against the recording with the current RTL. That confirms the split factories match Delphi
   for every case above. Report any case where it does not, without changing the transpiler.
3. **The construction context.** Implement the mechanism the design note describes under
   "Keeping the contract with real constructors", item 2, in the RTL (`src/Rtl`), as a small
   internal type with tests in `src/Rtl.Tests`:
   - the outer factory creates the context and calls the concrete constructor
   - the root constructor captures `this` before any other work of the chain
   - every constructor in the chain passes the same context
   - only the factory's catch marks failure and calls the captured object's virtual `Destroy`,
     once, after the chain has unwound
   - a child created during construction gets its own context
   - cleanup is marked attempted before `Destroy` runs, so a throwing destructor does not run
     twice, and its exception replaces the constructor's, as in Delphi

   Write a C# version of every probe case with real constructors and the context, in
   `src/Rtl.Tests`, and assert the same sequence of facts as the Delphi recording. No thread
   static or ambient state, no finalizer.
4. **Decision record.** Add a section to `ctor-design.md` (private) that states whether the
   context reproduces every recorded case, the exact API, and where it falls short. If a case
   cannot be reproduced, say which and stop there: the later briefs keep the guarded split
   factory for any family that depends on that case.

No game family uses the context in this brief. The existing test
`ComponentMetaclassRunsVirtualInitializerAndCleansUpFailures` stays.
