# Brief 4.1: the layouts as generated C# code, and the module load (U1, U2)

Milestones 4.1 and 4.2 of `docs/milestones.md`. Specification: `docs/specs/ui-layout.md` in full,
with decisions 1 and 2 of its section 1 as revised on 2026-10-26: the layouts become C# code that
creates each module's components with object and collection initializers, generated once from the
recovery's text forms. Read `parallel-tracks.md` in this folder first: its rules apply.

A first run of this brief started on a binary resource reader under the earlier decision. Its
partial work is in your worktree and in the private repository (`tools/forms`, `tests/forms`): keep
what serves the new design (the text form parser, the tree model, the checks) and drop the rest.

You write in your product worktree under `src/Layout` (the generated files and the small runtime
they need: fixup list, `Loaded` sequencing) and in the private repository under `tools/forms` and
`tests/forms`.

## What to build

1. **The generator**, a C# console tool under `tools/forms` (Roslyn `SyntaxFactory`, like the
   transpiler, never C# text), which reads the 79 text forms of `D:\git\aow\data\forms\AoW` with
   the grammar of section 3 and writes `src/Layout/<Module>.Layout.cs` for the 77 data modules: a
   partial class of the module (the generated module class in `src/Generated` is partial) with
   `InitializeComponent()`. Each component is created with its owner and parent as VCL streaming
   would, its properties set with an object initializer in the order of the form file (the order
   is behavior: setters run in that order), nested sub-objects (`Alignment.*`, `Font.*`) with
   nested initializers, string lists with collection initializers, sets with the shim's set
   construction, `#nnn` characters and the three binary blocks as byte data, handler assignments
   as method groups.
2. **The loading semantics** of section 4 in the generated code and a small runtime: the modules
   created in the `Application.CreateForm` order of section 4.1, `Loaded` called on each
   component after its module's tree is complete in the order `TReader` uses, references to a
   component of an already loaded module written directly, and references to a later module
   recorded as fixups that run when that module finishes, as `GlobalFixupReferences` does.
3. **Typing.** The generator needs each property's type and which names are handlers. The
   transpiler is frozen, so read them from its existing read-only commands (`resolve --dump`) or
   the generated C# in `src/Generated` with Roslyn, inside `tools/forms`. A property the generator
   cannot type is an error with its form file location.
4. **Checks**: `tools/forms/check.py` of section 8 (or its C# equivalent inside the generator) over
   the 79 files, and `dump.py`'s expected trees in `tests/forms/` compared with the tree the
   generated code builds at run time for every module.

## Done measure

1. U1: the generator reads all 79 files with zero errors, and every generated file compiles (the
   root solution builds with zero warnings).
2. U2: running every module's `InitializeComponent` in the order of section 4.1 leaves no pending
   fixup, and the built trees equal the expected trees of `tests/forms/` for all 77 modules.
3. A second generator run gives byte-identical files.
